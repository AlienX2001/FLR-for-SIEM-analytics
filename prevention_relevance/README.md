# Collective-Intelligence Prevention Relevance

`prevention_relevance` is a standalone experiment for comparing a proposed
organization change with historical STIX Indicators. It builds a typed graph
`G_new` from representative system and network logs, builds an IoC knowledge
graph from a STIX bundle, and ranks Indicators by their applicability to the
proposed environment.

The result is decision support for a human analyst. A high relevance score says
that an Indicator overlaps the proposed architecture or its operating context;
it does not prove that the proposed environment is vulnerable or malicious.

## Architecture

The command performs these steps:

1. Stream proposed system/network CSV records.
2. Reuse `field_aware_tokens()` and `_row_text()` from
   `federated_lr_pipeline.specialized_models` through
   `preprocessing_adapter.py`.
3. Construct `G_new` with typed nodes such as platform, process, file path,
   IP address, domain, protocol, and port, plus typed relations such as `runs`,
   `accesses`, `connects_to`, and `uses_port`.
4. Stream STIX objects and construct one neighborhood per Indicator. Exact STIX
   equality patterns are converted to typed observable nodes.
5. Optionally enrich Indicator neighborhoods with the predicted attack class,
   evidence categories, and feature tokens from `ioc_records.jsonl` and
   `explanations.jsonl`.
6. Compute direct-observable, node, edge, and contextual applicability scores.
7. Apply an evidence-eligibility gate, rank Indicators, and optionally evaluate
   the ranking against analyst labels.

The module does not call model training or inference and does not query online
services. It does not alter the federated or IoC-generation pipelines.

## Installation

The module uses the repository dependencies in `pyproject.toml`. In this
workspace, run it through the `LR` Conda environment:

```bash
conda run -n LR python -m prevention_relevance.run --help
```

## Example

```bash
conda run -n LR python -m prevention_relevance.run \
  --proposed-system-logs prevention_relevance/examples/proposed_system.csv \
  --proposed-network-logs prevention_relevance/examples/proposed_network.csv \
  --ioc-bundle prevention_relevance/examples/example_ioc_bundle.json \
  --config prevention_relevance/examples/similarity.yaml \
  --relevance-labels prevention_relevance/examples/relevance_labels.csv \
  --output-dir outputs/prevention-example
```

For IoCs generated by this repository, add the optional context files:

```bash
conda run -n LR python -m prevention_relevance.run \
  --proposed-system-logs proposed/system.csv \
  --proposed-network-logs proposed/network.csv \
  --ioc-bundle outputs/run_001/iocs/ioc_bundle.json \
  --ioc-records outputs/run_001/iocs/ioc_records.jsonl \
  --explanations outputs/run_001/explanations.jsonl \
  --config prevention_relevance/examples/similarity.yaml \
  --output-dir outputs/prevention-run
```

`--proposed-logs` accepts uncategorized CSVs. The system and network variants
record a category hint but do not bypass field-based extraction. `--assume-validated`
marks every input Indicator as validated and should be used only for an already
curated bundle. `--omit-historical-graph-output` avoids serializing the large
historical graph while retaining ranking output.

## Graph Schema

Node values are canonicalized by type. Domains are lowercase IDNA names, IPs
and networks use Python `ipaddress`, ports are validated integers, HTTP(S) URLs
are normalized, and Windows/POSIX paths use stable path normalization. Node and
edge IDs are deterministic SHA-256 identifiers derived from canonical values.

The proposed graph may contain:

| Node type | Example |
|---|---|
| `platform` | `windows` |
| `process` | `powershell.exe` |
| `process_path` | `c:\windows\...\powershell.exe` |
| `file_path` | `c:\finance\quarterly.xlsx` |
| `ip_address` | `203.0.113.20` |
| `domain` | `updates.example.com` |
| `protocol` | `tcp` |
| `port` | `443` |
| `feature` | a field-aware token from shared preprocessing |

Administrators can change CSV aliases in `field_mappings` without changing
Python code. If two populated aliases for one logical field conflict, that
logical value is omitted and the conflict is counted in graph metadata.
Target/ground-truth columns are excluded through the existing federated
preprocessing leakage safeguards.

## STIX Support

The reader supports JSONL STIX objects, a JSON list, one JSON object, or a STIX
Bundle. It recognizes exact equality patterns for:

- IPv4 and IPv6 addresses;
- domains, URLs, and email addresses;
- vulnerabilities;
- MD5, SHA-1, SHA-256, IMPHASH, and PEHASH values on `file` or `artifact`.

Unsupported compound or inequality patterns remain in Indicator metadata but
do not become direct observable nodes. The module preserves STIX relationships
whose endpoints are present. When project-specific context files are supplied,
the graph also links Indicators to their source events and evidence tokens.

## Similarity

For Indicator candidate graph `C` and proposed graph `G_new`, each candidate
node `u` receives a type weight and inverse-candidate-frequency factor:

```text
w(u) = type_weight(u) * [log((N + 1) / (df(u) + 1)) + 1]
```

The node component is weighted candidate coverage:

```text
S_node = sum_u w(u) max_v sim(u, v) / sum_u w(u),  v in G_new
```

Node similarity supports exact typed equality, IP-in-CIDR membership,
process/path basename agreement, and URL-host/domain agreement. The edge score
uses relation-equivalent edges and multiplies the two endpoint similarities.
`S_direct` is one only when the Indicator's exact observable occurs in
`G_new`. `S_context` measures configured attack-applicability requirements.

The final relevance score is:

```text
S = clip(
      a_direct*S_direct + a_node*S_node + a_edge*S_edge
      + a_context*S_context - lambda*platform_incompatibility,
      0, 1
    )
```

The component weights are normalized to sum to one. Except for an exact direct
observable match, a candidate must match at least the configured number of
distinctive nodes and have edge or context support. Generic protocols, common
ports, or configured generic processes cannot pass this gate alone.

`relevance_score` controls the decision bands. `priority_score` additionally
downweights unreviewed/rejected Indicators and incorporates an available model
risk probability. Risk changes triage order, not architectural relevance.

## Configuration

The version-1 YAML/JSON configuration supports:

- component, node-type, and match-method weights;
- relevant and analyst-review thresholds;
- evidence-gate and ego-neighborhood size;
- platform incompatibility penalty;
- CSV field aliases;
- relation aliases;
- generic values that cannot establish distinctiveness;
- attack-class applicability hypotheses;
- validated-only selection;
- optional field-aware feature-token enrichment.

Unknown fields, duplicate YAML keys, unsupported node types, malformed values,
and invalid thresholds fail validation. See
`examples/similarity.yaml` for a complete editable configuration.

## Outputs

The output directory contains:

| File | Contents |
|---|---|
| `proposed_change_graph.json` | Serialized `G_new` |
| `historical_ioc_graph.json` | Historical STIX graph, unless omitted |
| `ioc_relevance_rankings.csv` | Flat ranked results and JSON explanation |
| `ioc_relevance_rankings.jsonl` | Structured ranked results |
| `prevention_explanations.jsonl` | Matched/unmatched evidence per Indicator |
| `prevention_summary.json` | Counts and top-k Indicators |
| `prevention_run_config.json` | CLI inputs and resolved configuration |
| `prevention_metrics.json` | Optional metrics against analyst labels |

Writes are atomic. The CSV/JSONL rankings include all Indicators that pass the
configured validation filter, not only selected Indicators.

## Evaluation

An optional relevance-label CSV must contain:

```csv
indicator_id,relevant
indicator--...,true
indicator--...,false
```

The evaluator reports accuracy, precision, recall, F1, confusion matrix,
average precision, ROC AUC, NDCG, and precision/recall at `--top-k`. Analyst
labels must refer to Indicators in the ranking. The `analyst_review` band is
not counted as an automatic positive decision.

## Security and Limitations

- Proposed logs are a behavioral proxy for a planned architecture. Their
  completeness determines the quality of `G_new`.
- Exact IoC overlap is strong evidence of relevance, not proof of exposure.
- Attack-applicability mappings are administrative hypotheses and require
  expert review.
- Unreviewed generated IoCs should not be treated as validated intelligence.
- No fuzzy string matching, graph embedding, DNS resolution, or online lookup
  is performed.
- Current graph storage is in memory. Use
  `--omit-historical-graph-output` to reduce output I/O for very large bundles;
  very large knowledge banks may require a graph database in a later system.
- Similarity can prioritize preventive controls, monitoring, and analyst
  investigation, but it cannot establish that a future event will occur.
